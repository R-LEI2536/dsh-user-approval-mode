代价和边界边界

这个规则不猜危险 API，只看代码结构。 代价是：正常 JS 逻辑也会 ask；混合代码可能顶层 ask 后，子调用再 ask。 smart 仍依赖 LLM 和危险清单，可能被绕过。 真正的硬边界还是沙箱；要彻底不静默，宿主层得审批文件效果。

这段案例说明了什么

1. 顶层看代码，不看身份 顶层 run_code 不因为“它是顶层”就弹；先看代码结构。
2. 只有工具调用放行 只有 tools.* 调用（加接结果的变量和 return）才 allow。
3. 其它 JS 都 ask 出现运算、分支、循环、直接 API，或混合代码，就 ask。

新流程的完整判断

run_code 保留在 autoAllowTools 里。 分类插在“自动放行”返回之前，所以只影响顶层调用。

// tools/pre-execute if (exec.name === 'run_code' && exec.parent === undefined) { // 顶层调用：看代码，不看身份 if (mode === 'request' || mode === 'auto-edit') { return isToolCallsOnly(code) ? allow() // 只有工具调用：交给子调用 : ask(codeSummary(code)) // 其它 JS：ASK } if (mode === 'smart') { return smartPipeline(code) // 五步：危险清单 → 记忆 → LLM → 兜底 } return allow() // yolo / off：不查 } // 其它工具：现有工具族逻辑，不变 return familyGate(exec)

isToolCallsOnly 是语法白名单，不是危险清单。不认识的写法默认 ask。

模式规则

request / auto-edit 的规则只有一条：顶层只放行“只有工具调用”的代码。 纯工具调用交给子调用；出现其它 JS，就 ask。

模式顶层 run_code结果子调用
request 只有 tools.* 调用 → 放行；其它 JS → ask 纯工具 ALLOW
其它 ASK		 只读 allow；编辑 / shell / other ask
auto-edit 只有 tools.* 调用 → 放行；其它 JS → ask 纯工具 ALLOW
其它 ASK		 编辑 allow；只读 allow；shell / other ask
smart 五步流水线：危险清单 → 只读 git 快路径 → 会话记忆 → LLM → 兜底 danger 或 LLM ask → ASK
LLM approve → ALLOW
无 LLM → ASK		 同现有 smart：shell 走五步；只读 allow；other ask
yolo 不查 ALLOW allow
off 不查 ALLOW 闸门不拦截

严格模式只问代码结构；子调用还是按族裁决。

三类代码，一个兜底

闸门只看结构，不看危险 API。只有工具调用放行；出现其它 JS 就 ask。 变量和 return 只用来接结果，算工具调用的一部分。

只有工具调用 → ALLOW

await tools.read({ file_path: 'README.md' })
const r = await tools.read({ file_path: 'README.md' })
return r.lines.length

只有工具调用，和接结果的变量 / return。子调用照旧裁决。

工具调用 + JS → ASK

const r = await tools.read({ file_path: 'README.md' })
if (r.lines.length > 100) {
  await tools.write({ file_path: 'big.txt', content: 'big' })
}

出现 if 和比较运算，就不再是纯工具调用。

只有 JS → ASK

import { rmSync } from 'node:fs'
rmSync('./dist', { recursive: true })

没有 tools.* 调用，全是 JS。

不在白名单 → ASK（兜底）

const f = globalThis['fe' + 'tch']
await f('https://example.com')

看不懂的写法不猜，默认 ask；不默认 allow。

边界 const r = await tools.read(...) 和 return r.lines.length 算“只有工具调用”； 一旦出现运算、分支、循环、字符串拼装、import / require、process / globalThis、 eval / fetch、直接 fs、动态成员（obj[expr]）、未知语法，就 ask。

smart 的五步

smart 是唯一的“分类”路径。代码作为 command 送进去，可能 ask，也可能 allow。

  1. 危险清单目前是 shell 正则。fs.rmSync 不命中，继续下一步。缺陷：漏 JS 危险写法
  2. 只读 git 快路径对代码不匹配，继续。后续代码流程可以去掉这一步。
  3. 会话记忆key 用代码文本。同一段代码批过，TTL 内直接 allow。
  4. LLM 分类把代码作为 command 送 LLM。approve → allow；ask → ask。缺陷：默认提示词偏 shell；代码会发给外部 LLM
  5. 兜底没有 LLM、超时、异常 → ask。

smart 不是保证。动态写法、提示词偏置、模型判断都可能让它放行。

已知代价

正常 JS 逻辑会 ask

只要出现运算、分支、循环，就不再是纯工具调用。严格模式会明显更吵。

“只有工具调用”的边界要定

变量、return、取值算不算 JS，需要写死。边界越宽，白名单越难维护。

可能双弹

混合代码顶层 ask 后，代码里的 tools.write、tools.bash 子调用还会各自 ask。

smart 仍可能漏

危险清单是 shell 的；LLM 也可能被写法或提示词带偏。它不是硬边界。

源码外发

smart 下代码会发给外部 LLM。这是接受的成本。

代码摘要还没接

ask 时弹窗里暂时看不到代码。审批是盲的，属于后续工作。

粒度是整段代码

批准的是整个顶层调用，不是单个文件操作。

没有按文件批准

不能只批“删 ./dist”，不批同一段代码里的其它操作。

已否决 / 边界

  • 一律 ask：纯工具调用也弹，太吵；顶层不应该因为“它是顶层”就弹。
  • 危险清单决定放行：可绕过；漏检会变成静默放行。
  • 顶层无条件 allow：fs.rmSync 这种只有 JS 的代码会静默执行。
  • 拿掉 autoAllowTools：yolo / off 也会弹，做不到按模式区分。
  • 只靠 LLM 判断 request / auto-edit：贵、慢、源码外发。
  • 把白名单当硬边界：不行。它只是静态分类。
